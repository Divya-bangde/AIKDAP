# AIKDAP visualization audit

Completed 15 October 2026. Inspection and evidence collection: 14–15 October 2026.

## Assessment

The interface has a coherent visual language: consistent cards and spacing, dark/light theme tokens, restrained status colors, readable mathematical typesetting, and a useful connection between answers and cited evidence. Basic charts, equations, diagrams and paper maps render successfully in the tested examples.

The main problem is the contract between data, requested visual and rendered result. A chart can look polished while containing unsupported values, dropping a requested metric, normalizing a partial result, or displaying a different chart type from the request. Correctness and inspectability should take precedence over adding more visual effects or chart types.

Recommended order: **verify plotted values → preserve chart intent and every metric → validate chart structure → make context and partial data explicit → improve accessible interaction → optimize rendering and loading.**

## Scope and evidence

- Read the research/chart/diagram/equation components, analytics chart builder and result card, paper map, evidence workspace, source mix, theme tokens, relevant backend schemas, synthesis flow, analytics plan validation and existing tests.
- Inspected the real landing/sign-in UI and, once a signed-in session was available, the command center and two saved research runs.
- Inspected actual production components in a temporary local fixture page with synthetic data. This separated renderer behavior from model behavior without creating accounts, modifying projects, or calling inference services.
- Tested desktop at 1440 × 900 and a narrow viewport requested at 390 × 844. Usable document width was sometimes 375 px because of the browser scrollbar. Waited for Plotly resize completion before assessing overflow; transient resize overflow was not treated as a defect.
- Tested light and dark themes in the synthetic preview. No persistent user theme preference was changed.
- Existing targeted frontend tests: **55 passed across six files**. Existing targeted backend tests: **35 passed**, one dependency deprecation warning.
- Ran additional offline probes against the real chart builder, schema validators and synthesizer. No real model response was generated by these probes.
- Screenshots, logs and the synthetic fixture source are in `docs/visualization-evidence-2026-10-14/`.

The synthetic fixture is a renderer test, not a screenshot of a user's analytics project. The saved research runs are pre-existing records; their behavior is not a fresh evaluation of the currently configured model. A complete screen-reader audit, every chart type, dense/large citation graphs, print/PDF output and all device/browser combinations were not tested.

No application implementation was changed. Temporary fixture files were moved out of the application into the evidence directory. Pre-existing working-tree changes were preserved.

## V01 — Verify plotted values, not only answer citations

**Evidence:** `backend/app/agents/planner/synthesis.py:450` parses the visual, validates answer citation IDs and verifies claims. The visual is retained when the overall grounding status is grounded (`:512`), but its trace values are not passed through an equivalent evidence check. The prompt forbids invented chart numbers, which is a useful instruction but is not an enforcement mechanism.

An offline gateway double returned a valid citation to a passage saying **“The reported count is 42.”**, plus a bar trace with **999999**. The real `GroundedSynthesizer.synthesize` returned:

```json
{"source_value":42,"grounding_status":"grounded","visualization_kept":true,"plotted_values":[999999]}
```

This is a deliberately adversarial test, not an allegation that a live model produced those numbers. It demonstrates that the acceptance boundary currently permits the mismatch.

**Change:** Prefer deterministic chart construction from extracted tables or validated analytics results. For research charts, require source references for data points or series and verify values, units and transformations. Label measured, derived, illustrative and user-entered data explicitly. Withhold a visual that fails verification while preserving an otherwise usable answer and explaining why the visual is unavailable.

**Acceptance:** A passage containing 42 cannot authorize a plotted value of 999999. Supported transformations such as unit conversion retain their input references and formula. A user can open the evidence behind a plotted value.

## V02 — Preserve every selected metric

**Evidence:** `frontend/src/features/business-analytics/analysis-chart.ts:23` builds one trace per series using only `chart.y[0]`. The backend plan permits multiple metrics and multiple chart y fields.

For a requested comparison of revenue and cost by region, the result table contained both columns. The chart showed only revenue for West and East. The legend identified regions but did not reveal that cost had been omitted. The standalone probe reproduced the same behavior.

**Change:** Generate traces for each intended `(series, metric)` pair, with unambiguous legend names. Where metrics have incompatible units, use separate panels or require an explicit supported axis policy. If that presentation is not supported, reject the plan and explain the limitation before rendering.

**Acceptance:** Two metrics across two regions create four correctly labelled traces or two explicit metric panels. No selected metric disappears silently. Add coverage for both grouped bars and lines.

Screenshot: `analytics-comparison-desktop.jpg`.

## V03 — Validate chart data and rendering budgets

**Evidence:** `backend/app/modules/research/schemas.py:218` accepts a chart if any trace value is a nonempty list. It does not establish that this is a supported drawable trace.

The actual validator accepted all of these cases:

| Probe | Input problem | Result |
| --- | --- | --- |
| Metadata-only trace | `{"metadata":["not a plotted series"]}` | Accepted |
| Incompatible paired axes | Three x values and one y value for scatter | Accepted |
| Non-finite number | A y value of positive infinity | Accepted |
| Incorrect dimensionality | `chart3d` containing a 2D scatter with no z | Accepted |

**Change:** Use a discriminated trace schema for supported chart types. Check required fields, paired-array lengths, rectangular surface/heatmap grids, finite numbers, numeric/category axis compatibility, pie constraints and 2D/3D consistency. Set explicit limits for traces, points, cells and serialized bytes. Validate layouts rather than treating arbitrary dictionaries as a complete contract.

**Acceptance:** These four probes are rejected with actionable reasons; correctly formed bars, scatter plots, pies and supported 3D surfaces remain valid. Large specs fail safely before browser rendering.

## V04 — Preserve requested chart intent and expose unmet visual requests

**Observed saved bar request:** Research run `435d91f5-82e2-4374-9d17-2adfc54f6ac9` explicitly asks for a bar chart. The rendered DOM had **zero bar paths and one scatter line**. The screenshot shows a connected line across years.

**Relevant code:** `backend/app/modules/research/schemas.py:227` repairs `{x,y}` point lists. String x values become bars; numeric x values become `scatter` with `lines+markers`. Numeric categories such as years cannot carry their intended bar-chart type through this repair rule.

**Observed saved comparison request:** Research run `93e7d9c2-8508-4edb-9e25-08aa3c7fa789` asks for baseline/warm-up loss curves but presents prose and no chart. The page has a grounded outcome and no separate visual-output status or repair control. The answer describes incomplete evidence; the UI does not independently tell the user whether the requested visual was produced.

**Change:** Represent visual intent separately from output, including requested trace type, axis semantics and requested series. Record `produced`, `not_enough_data`, `unsupported` or `failed` with a reason. Preserve the requested bar/line type when normalizing points. Offer a bounded repair path when a visual fails validation, rather than repeatedly rerunning unrelated stages.

**Acceptance:** A yearly bar request renders bars. A request that cannot produce a visual shows an explicit reason and next action. A text-only successful answer is distinguishable from a completed requested deliverable.

Screenshots: `saved-research-bar-desktop.jpg`, `saved-research-bar-mobile.jpg`, `saved-research-line-desktop.jpg`.

## V05 — Make partial pie-chart denominators explicit

**Evidence:** `analysis-chart.ts:11` passes displayed rows directly to Plotly pie values. Analytics results are limited after aggregation. `AnalysisCard.tsx` exposes “Showing 2 of 10” in a collapsed disclosure, while the pie itself displays 60% and 40% as a complete circle.

Those percentages describe the displayed subset, not necessarily the complete set of categories. They are not mathematically wrong for that subset, but the visual lacks a prominent denominator/scope explanation.

**Change:** Either produce the complete distribution, compute an accurate “Other” category from the full result, or label the visual “Share of displayed categories” with a visible partial-data notice. Do not calculate “Other” from row count alone. Reject negative or otherwise unsuitable values and bound category counts.

**Acceptance:** A limited two-category result cannot appear to represent all ten categories without explanation. Full and partial shares have distinct visible labels.

Screenshot: `partial-pie-desktop.jpg`.

## V06 — Give line ordering explicit semantics

**Evidence:** The chart builder preserves input row order. A numeric probe with x `[3,1,2]` produced that same connected order. The browser fixture displayed months as March → January → February. The backend handles chronological sorting for an explicit `time_bucket`, but ordinary numeric/date columns and month-name categories can still arrive without that policy.

**Change:** For trend charts, sort each series by its validated numeric/date axis. For ordinal categories, use an explicit domain order. Preserve intentional path/trajectory ordering only when the chart contract says it is intentional. Do not alphabetically sort month names or blindly sort every connected scatter plot.

**Acceptance:** Unsorted trend rows produce the intended chronological progression; an intentional trajectory retains its declared path. Missing values and gaps have an explicit policy.

## V07 — Add a consistent, inspectable chart frame

**Evidence:** `PlotlyVisualization.tsx:24` supplies margins, theme and a fixed 380 px height but does not require labels or units. The analytics builder sets an x-axis title without a y-axis title. A research fixture and the saved yearly chart rendered tick values without named axes. Research charts have no built-in data table; analytics has a useful expandable table.

The saved yearly chart is based on a report explicitly describing its figures as illustrative sample data. That qualification is visible in its source/prose, but is not a stable chart-level origin label. “Grounded” should communicate source attribution without implying that illustrative values are real-world measurements.

**Change:** Standardize a chart frame with a meaningful title, short finding, axis names and units where applicable, source/data origin, filters/time window, partial-data status, accessible table, and download controls. Keep the actual data inspectable. Do not invent currency or physical units when the dataset does not specify them.

Associate concise and detailed text alternatives with charts and diagrams. W3C recommends a short identification plus a representation of the essential values/relationships for complex images. [W3C complex-image guidance](https://www.w3.org/WAI/tutorials/images/complex/)

**Acceptance:** A standalone exported/shared chart retains enough context to interpret it correctly. A research plot is usable without inferring axis meaning from the surrounding paragraph. Illustrative data is labelled beside the visual.

## V08 — Provide keyboard access to the paper map

**Evidence:** `PaperMap.tsx:165` gives the canvas wrapper `role="img"` and a summary, but selecting a paper is wired only through `onNodeClick` (`:197`). The browser accessibility tree lists the legend and map summary but exposes no per-paper selection controls. Existing unit tests replace the graph with HTML buttons, which makes their test interaction more accessible than the production canvas.

**Change:** Add a synchronized searchable paper list/table with focusable controls opening the same detail panel. Provide explicit fit/reset/zoom controls and a pause option where appropriate. Preserve focus when opening/closing details. Explain arrow direction and what node size means; global citation count is not the same as relevance to the user's question.

This addresses actual functionality, not only alternative wording. Keyboard users need equivalent access to node selection. [W3C keyboard guidance](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html)

**Acceptance:** A keyboard user can find any paper, inspect it, open its source and access the existing import action without canvas pointing. Screen-reader and real-browser checks cover the production control path.

Screenshot: `paper-map-desktop.jpg`.

## V09 — Improve chart contrast and redundant encoding

The light-theme chart colors in `frontend/src/index.css:92` include these contrasts against a white card:

| Series | Color | Contrast |
| --- | --- | --- |
| 3 | `#1baf7a` | 2.82:1 |
| 4 | `#eda100` | 2.17:1 |
| 5 | `#e87ba4` | 2.69:1 |

These are below 3:1 for essential graphical marks against that background. The finding is specifically about applicable chart lines/marks, not a blanket declaration about every use of these colors or whole-site compliance. [W3C non-text contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)

**Change:** Adjust applicable tokens or add sufficiently contrasting outlines. Add line styles/marker shapes and stable series identity so color is not the sole distinction. Give many-series charts a selection/aggregation strategy instead of relying on repeated palette cycles. Maintain theme-specific checks.

**Acceptance:** Essential marks meet contrast requirements against actual adjacent backgrounds. Series remain distinguishable in grayscale and common color-vision simulations. Filtering/reordering series does not unexpectedly change their identities.

## V10 — Render a valid single-citation graph

**Evidence:** `PaperMap.tsx:155` shows the empty state when `graph.links.length < 2`. With three papers and one valid edge, the UI says “Your matched papers don't cite each other yet.” That message contradicts the data.

**Change:** Render a graph with one edge or show a simple relationship card. Reserve the no-citations state for zero edges and explain unmatched/isolated papers separately.

**Acceptance:** Zero, one and multiple links have truthful, distinct behavior. A single valid citation remains selectable.

Screenshot: `one-citation-empty.jpg`.

## V11 — Expose physical values for logarithmic controls

**Evidence:** `InteractiveEquationCard.tsx:145` transforms slider coordinates using logarithms. In the browser fixture, the mass numeric field displayed **1 kg**, while the slider accessibility value was approximately **−0.001** and had no `aria-valuetext`.

**Change:** Set a meaningful accessible label, unit and `aria-valuetext` based on the actual physical value; keep the numeric input alternative. Explicitly identify logarithmic axes and consider a user-controlled linear/log policy rather than an unannounced scale transition. Preserve the useful current reference curve and stable-axis behavior.

**Acceptance:** Assistive technology announces “Mass, 1 kilogram” rather than the transformed slider coordinate. Slider and number field stay synchronized, and scale changes are understandable.

## V12 — Keep the visual task legible on mobile

**Observed positives:** Tested cards and equation controls reflowed without persistent horizontal page overflow after rendering/resize completion. Numeric equation input remained available. This was a targeted fixture check, not proof that every signed-in screen is responsive.

**Problems:** The three-node horizontal Mermaid example is scaled down to fit a phone, producing very small labels. The wrapper applies `max-w-full` without a zoom/detail view. On the real saved research page, the entire long question is used as the large heading, followed by lengthy prose; the requested chart falls well below the first screen.

**Change:** Offer a larger diagram view with pan/zoom or a suitable vertical layout and a textual relationship alternative. For visual requests, consider a concise run title, full-question disclosure, brief finding and chart before the longer explanation. Preserve source access and do not hide important qualifications to make the page shorter.

**Acceptance:** Diagram labels remain readable at narrow widths. The user can reach and understand the requested chart without scrolling through a duplicate full-length prompt and explanation first. Check keyboard, touch and 200% zoom.

Screenshots: `diagram-mobile.jpg`, `equation-mobile.jpg`, `saved-research-bar-mobile.jpg`.

## V13 — Refresh the equation accent on theme changes

**Evidence:** `InteractiveEquationCard.tsx:199` and `:554` memoize `accentColor` with no dependencies. In the theme-switch probe, the primary CSS token changed from `243 75% 59%` to `243 80% 70%`, but both equation line strokes remained `rgb(80,72,229)`.

**Change:** Derive this color through the same theme subscription already used by the general Plotly renderer. Test the curve, reference traces, markers and labels after switching themes without remounting the card.

**Acceptance:** The curve uses the current theme immediately and maintains contrast. No input values or axis state are lost during the theme switch.

Screenshots: `equation-desktop.jpg`, `equation-dark-desktop.jpg`.

## V14 — Make rendering recovery and chart controls consistent

**Evidence:** The generic Plotly wrapper has a Suspense loading message but no local render-error fallback or visible table alternative. Mermaid does provide a useful raw-source fallback, though it does not explicitly explain that diagram rendering failed. Generic plots expose default modebar actions including “Share chart…”, while experiment charts disable the modebar entirely.

**Change:** Use a local error boundary plus renderer error handling, a retry/view-data path and a clear status message. Deliberately choose export/interaction controls for each surface. Do not expose an unexplained generic sharing workflow; do not remove useful fit/reset/export functionality without an equivalent. Add diagram download and chart data export with provenance where appropriate.

**Acceptance:** A failed render does not remove an otherwise usable answer. Users can inspect the data and understand the failure. Exported images remain legible in light/dark contexts and retain captions/units; export behavior still needs dedicated verification.

## V15 — Update the explanatory pipeline visualization

**Evidence:** `LandingStory.tsx:27` describes its list as the real processing order: Collect → Understand → Embed → Retrieve → Rerank → Ground → Synthesize. `backend/app/modules/assets/processing/pipeline.py:169` embeds before enqueueing AI understanding, and understanding is best-effort rather than a prerequisite for retrieval. The landing graphic also presents the research path as a single strict sequence, omitting fallback branches.

**Change:** Clearly label the figure as a simplified conceptual overview or update it to show the actual ingestion path, optional understanding branch, query-time retrieval and fallback behavior. Keep decorative illustrations visibly distinct from live metrics; the current retrieval illustration's explanatory disclaimer is a good pattern.

**Acceptance:** A user does not infer that document profiling must finish before search works, or that every research run follows exactly the same seven linear stages.

## What to retain

- Shared theme tokens and theme-aware general Plotly/Mermaid rendering.
- Lazy loading of large renderers and the paper map.
- Restrictive Mermaid security mode and KaTeX's non-trusting defaults.
- Evidence verdict text/icons alongside colors, source viewing and PDF passage highlighting.
- Explicit illustrative equation-value notices and deterministic equation evaluation.
- The stable/widen-only equation axis behavior and reference curves, which help show actual changes when inputs move.
- Analytics' expandable result table and computation explanation.
- Honest pipeline status labels, including skipped/failed states.
- Explanatory disclaimers on decorative landing-page retrieval quantities.

## Loading and performance

Both generic research plots and experiment plots import the full `plotly.js-dist-min` distribution. Minification does not make it a selective trace bundle. Equation cards also load mathjs, and Mermaid carries multiple diagram capabilities.

The final production build passed, including TypeScript compilation. Vite measured the generic Plotly chunk at **4,279.53 kB minified / 1,324.70 kB gzip**, the equation chunk at **682.61 / 197.29 kB**, and the Mermaid renderer chunk at **659.95 / 159.90 kB**. These are build-output sizes, not measured user network timings. Vite emitted large-chunk warnings. Existing lazy loading reduces when these bytes are requested, not the size of the renderer itself.

Recommended work:

1. Keep lazy loading and introduce explicit chart/diagram complexity budgets.
2. Use a smaller registered 2D trace set for ordinary analytics; load 3D separately when required.
3. Benchmark parsing and interaction on a slower device, not only bundle bytes.
4. Observe container resize for drawer/sidebar/tab changes and verify stable charts after resize; do not mistake transient autosize work for a lasting defect.
5. Add deliberate downsampling/aggregation for large series while preserving the full data alternative and indicating the transformation.
6. Prefer 2D heatmaps/contours to 3D when they communicate the requested comparison more clearly; retain 3D for tasks where it adds information.

## Regression coverage to add when implementing fixes

Existing tests passed because the problematic edge cases are not covered, not because those behaviors are correct. Add focused cases for:

- A source-valid answer with an unsupported plotted number.
- Two metrics × two groups, including incompatible units.
- Numeric years explicitly requested as bars.
- Missing visualization output despite a visual request.
- Limited pie results and invalid pie values.
- Unsorted numeric/date trends and intentionally ordered trajectories.
- Non-finite values, mismatched arrays, malformed 3D grids and oversized specs.
- Zero/one/many citation edges, plus production keyboard node selection.
- Physical `aria-valuetext` on log sliders and live theme changes.
- Narrow viewport, long labels, chart error fallback and export context.

Use real-browser checks for canvas/Plotly/diagram behavior. Component mocks remain useful for logic, but cannot establish real graphical accessibility or visual fidelity.
